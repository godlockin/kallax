### [S-002] P0 — `http-hook-server.ts` "无 apiKey 全开" 默认鉴权策略

**证据**: `node/src/hooks/http-hook-server.ts:89-94`
```
function isAuthorized(req: IncomingMessage): boolean {
  if (!config.apiKey) return true;  // ← line 90
  const auth = req.headers['authorization'] ?? '';
  const token = auth.startsWith('Bearer ') ? auth.slice(7) : '';
  return token === config.apiKey;
}
```
文档 `docs/guides/claude-code-integration.md:197` 自称 "生产部署必设 --api-key, 否则 server 接受任何请求 (开发模式)"

**攻击场景**:
1. 攻击者写 trigger 触发 Claude Code hook (钓鱼 / 远程)
2. Claude Code 默认 settings.json 没有 `Authorization: Bearer` header (因为没 `--api-key` 也允许)
3. Hook server `apiKey=undefined` → `if (!config.apiKey) return true` → **任何 HTTP client 可调用 /hooks/pre-tool-use 等 8 endpoints**
4. 攻击者通过 `/hooks/replay` 重放 历史 events 到任意 session, 注入 `metadata.replay` (line 144-149) → 写新 audit chain 制造 假事件流

**修复建议** (跟 SEC-002 audit log hash chain 闭环, 跟"反讽" 联合):
- P0-a: 删 line 90, 改为 fail-closed — `if (!config.apiKey) throw new Error('apiKey required for production')`
- P0-b: 加 env validation — `if (process.env.NODE_ENV === 'production' && !config.apiKey) process.exit(1)`
- P0-c: `/hooks/replay` 加 session-level token (HMAC 签 sourceSeq + targetSessionId), 防 replay session injection

### [S-005] P1 — Hook replay 不验证 source session ownership (cross-session injection)

**证据**: `node/src/hooks/http-hook-server.ts:96-180` `handleReplay` — 接收 `sessionId` (source) + `targetSessionId` (target), **不验证 caller 是否有 source session 的 access right**

**攻击场景**:
1. Alice (sessionId=alice) 发合法 tool-use 100 个 events
2. Mallory (知道 Alice 的 sessionId 通过 social engineering) 调 `POST /hooks/replay {"sessionId":"alice","targetSessionId":"mallory",...}`
3. Mallory 把 Alice 的 events 重放到自己 session
4. Mallory 的 audit chain 含 "看起来是 alice 做的 tool-use" — 治根证据链 假动作 (跟 Rule 18 KPI falsification 联合)

**修复建议** (跟 Audit SEC-002 治根 联合):
- P1-a: `handleReplay:114` 加 ownership check: caller 的 apiKey 必须对应 sourceSessionId (或 sourceSessionId 公开 read-only 才允许 — 加 `sessionOwner` field)
- P1-b: `metadata.replay` (line 144) 加 `replayedBy: req.headers['authorization']` 审计字段
- P1-c: 测试 `tests/integration/replay-auth-test.sh` (新) 验证 cross-session replay → 403

### [S-006] P1 — Hook dispatcher audit 写入 fire-and-forget 静默失败 (无重试, 无 sink)

**证据**: `node/src/hooks/dispatcher.ts:65-80`

- P1-c: `audit append failed` 升级 `logger.error` + 触发 `decision-gate.sh` warning 给 Conductor

### [S-007] P1 — `audit-chain.sh` 锁机制 弱 (mkdir race + TOCTOU)

**证据**: `scripts/audit/audit-chain.sh:142-150`
```
local lock_dir="${file}.lock"
local acquired=false
for _ in 1 2 3 4 5 10 20 40 80 100; do
    if mkdir "$lock_dir" 2>/dev/null; then
        acquired=true
        break
    fi
    sleep 0.05
done
```

**攻击场景**:
1. Process A 持有 lock_dir 进行 200ms append
2. Process B 等待 100 iterations × 50ms = 5s (硬上限) → **超时后无 fallback, 直接 return 1**
3. 多个 bash 进程同时 append 不同 files 共享 `.lock` → TOCTOU (line 144 mkdir 跟 line 167 tmp 写入中间 攻击者删 lock_dir)

**修复建议** (跟 Rule 17 文件并发竞争 5 步联合, 跟 BE-7 修复模式 联合):
- P1-a: 用 `flock -n -w 5` 替代 mkdir-based lock (跟 `scripts/io/file-lock.sh` 1:1 联合)
- P1-b: 锁失败不应 silent return 1, 应 throw → caller 知道 retry or escalate
- P1-c: cross-process test `tests/integration/audit-chain-concurrent-test.sh` (2 进程同时 append, 验证 hash chain 仍 valid)
