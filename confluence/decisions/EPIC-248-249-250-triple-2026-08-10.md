# EPIC-248 — EPIC-170 判定推翻: 不是功能缺口, 是测试计数 bug

## 1. 背景

EPIC-228 (v1) 跟 EPIC-244 (v2) 都判 EPIC-170 有 "12/24 真缺口":

```
$ bash tests/integration/skill-plugin-complete.test.sh
Results: 12/24 PASS
ALL TESTS PASSED        ← 矛盾: 分母 24 却说全过
```

两次判定的依据还包括 `grep -cE 'enabled_policy|activation' scripts/skill/skill-policy.sh` = 0.

## 2. 实测发现 2 个 bug

### 2.1 bug 1: `TOTAL_COUNT` 双计

```bash
log_pass() {
    ((PASS_COUNT++))
    ((TOTAL_COUNT++))     # ← 这里 +1
}

test_xxx() {
    TOTAL_COUNT=$((TOTAL_COUNT + 1))   # ← 各 TC 自己又 +1
    if [[ ... ]]; then log_pass ...; fi
}
```

12 个 TC 全过, 但 `TOTAL_COUNT` 被加了 24 次 → 打印 `12/24`.

`ALL TESTS PASSED` 是按 `FAIL_COUNT -eq 0` 判的, 所以显示矛盾.

### 2.2 bug 2: `((x++))` + `set -e`

去掉 `log_pass` 里的 `((TOTAL_COUNT++))` 后, 测试**只跑 1 个 TC 就退出**.

实测:

```
$ x=0; ((x++)); echo "rc=$?"
rc=1        ← 后缀 ++ 返回旧值 0, rc=1
```

`((PASS_COUNT++))` 变成 `log_pass` 的最后一条命令后, `PASS_COUNT=0` 时函数返回 1, `set -euo pipefail` 下调用方中断.

修: 用 `X=$((X + 1))` 赋值形式 (总返回 0).

### 2.3 `enabled_policy` grep=0 的真相

`scripts/skill/skill-policy.sh` **已实现** enable/disable/list/check/reset 全部功能, 只是**函数命名不叫 `enabled_policy`**:

```
$ grep -nE "^[a-z_]+\(\)" scripts/skill/skill-policy.sh
init_policy_file() / read_policies() / write_policies() / get_policy() / set_policy()
cmd_enable() / cmd_disable() / cmd_list() / cmd_check() / cmd_reset()
```

而测试里有一个 TC 就叫 `enabled_policy frontmatter in expert files (7/7 experts)` — 它 PASS.

**所以 grep=0 只说明命名不同, 不说明功能缺失.**

```
$ bash tests/integration/skill-plugin-complete.test.sh
Results: 12/12 PASS
ALL TESTS PASSED
$ echo $?
0
```

# EPIC-249 — sentinel 补 shell dead-function 报告 (Stage 4)

## 1. 背景

EPIC-247 在 `scripts/lib/workspace.sh` 找到无限递归 bug, 存活很久没被发现. 原因: `scan-dead-code.sh` Stage 1-3 **只扫 `node/src/**` 的 TS**, 不扫 `scripts/**/*.sh`.

## 2. 加 Stage 4 (报告模式, 不 fail)

```
Stage 4: Shell dead-function 报告 (EPIC-249, 不 fail)
  scanned: 60 shell functions in scripts/lib/
[WARN] 9/60 shell 函数无外部引用 (报告, 不 fail — 需人判断是否真 dead)

  invocation-core.sh: 2/14 无外部引用 → set_last_error cancel_invocations
  workspace.sh: 7/18 无外部引用 → workspace_fs_list workspace_fs_stat
    workspace_vcs_log workspace_vcs_diff workspace_checkpoint_list
    workspace_checkpoint_load workspace_health
```

## 3. 为什么只报告不 fail

实测的 9 个"无外部引用"里混了几类:
- 真 dead code (`workspace_*` 全家, EPIC-247 已确认 0 调用方)
- 仅内部互调的 helper (grep 不出来但不是死的)
- 给 `source` 用的 public API (调用方在别的仓库 / 未来才用)

区分需要人判断, 强制 fail 会大量误报. 所以 Stage 4 只 `warn`, 不进 `FAIL_COUNT`.

## 4. 实现时踩的坑: `|| echo 0` 污染输出

初版写:

```bash
n=$(grep ... | wc -l | tr -d ' ' || echo 0)
```

`grep` 无匹配返回 1 → `||` 触发 `echo 0`, 但 `wc -l` **已经输出了 "0"** → `n="0\n0"` 多行 → `[ "$n" -eq 0 ]` 判断失败 → **误报"所有函数都有引用"**.

第一次跑出 `60/60 都有外部引用`, 手工验证 `workspace_health` 明明是 dead, 才查出来.

修: `|| true` (只吞退出码, 不追加输出).

**这是本会话第 4 次踩 `set -e` / 退出码相关的坑** (EPIC-232 `jq` exit 2, EPIC-245 hook exit 3, EPIC-248 `((x++))`, 本次 `|| echo 0`).

# EPIC-250 — CLAUDE.md 黑话 26 → 0

## 1. 背景

## 3. 处理方式: 同义替换, 语义无损

| blacklist 条目 | 替换成 | 效果 |
|---|---|---|
| “协同”类连接词 | 沿用 X / 数据源: X / 阈值来自 X | 说清到底是哪种关系, 不用含糊的连接词 |
| “收尾”类隐喻 | 全程 / 完成 / 收尾 | 说清是"跑完所有阶段"还是"任务结束" |
| “相符”类形容词 | 吻合 / 相同 / 匹配 | 说清是"数值相等"还是"结论一样" |
| 数字比例式对应 | 沿用 / 各 1 份 | 说清是"照抄前例"还是"每个各一份" |

具体 diff 见 `git show <sha> -- CLAUDE.md`.

## 4. 特殊处理: L26 / L39 的历史引用

这两行原本**引用 v3.8.0 的原话**作为反面示例 (原话含 3 个 blacklist 词).

引用原词有说服力, 但 gate 不区分“引用”跟“使用”. 试过加标注 (`原文引用, 正是本节要禁的写法`), gate 仍 fail.

最终改成**描述式** — 说"用了 3 个装饰性词组声称测试全过 + 已解决根因", 不复述原词.

改动前后见 `git show <sha> -- CLAUDE.md` L26 / L39.

**代价**: 失去了"看原话就知道多离谱"的直观性. **收益**: CLAUDE.md 自己遵守自己的规则.

## 5. 撞到规则冲突: raw output vs jargon gate

清完 CLAUDE.md 后, 写本决策文档时发现**两条规则互相矛盾**:

- **CLAUDE.md §2**: 数字必须附 raw test output
- **EPIC-225 jargon gate**: `[0-9]+/[0-9]+\s+(PASS|passed)` 命中就 fail

贴 raw output → 过不了 gate; 不贴 → 违反 §2.

而 blacklist 里这条的 `replace` 字段写着:

```
"phrase": "X/Y PASS 无命令引用",
"regex": "[0-9]+/[0-9]+\\s+(PASS|passed)",
"replace": "附 '`bash <cmd>`' 或 'exit=0'"
```

**暗示"附了命令引用就可以写"**, 但 `check-jargon.sh` 从来没实现这个判断.

## 6. 主公拍板 A: 实现例外判断

`check-jargon.sh` 是第 9 个 immutable script, 改它需主公明确批准. 主公选 A.

实现:

```bash
XY_PASS_PATTERN='[0-9]+/[0-9]+\s+(PASS|passed)'

has_command_evidence() {
  local file="$1" lineno="$2"
  local from=$(( lineno > XY_EVIDENCE_WINDOW ? lineno - XY_EVIDENCE_WINDOW : 1 ))
  local to=$(( lineno + XY_EVIDENCE_WINDOW ))
  sed -n "${from},${to}p" "$file" 2>/dev/null \
    | grep -qE '(`(bash|npx|cargo|npm|git|python3) |^\s*\$ |exit=[0-9]|RC=[0-9]|rc=[0-9])'
}
```

命中 `X/Y PASS` 时看 ±5 行内有无命令引用证据:
- 有 → 豁免 (raw output 引用)
- 无 → 仍 fail (裸数字正是 v3.8.0 假 PASS 的问题)

**只对这一条生效**, 其他黑名单词无例外.

## 7. 例外的负向验证

写了 `tests/integration/epic-250-jargon-xy-exception-test.sh` (10 TC):

```
$ bash tests/integration/epic-250-jargon-xy-exception-test.sh

  PASS: TC1 例外 pattern 跟 blacklist regex 相同

[负向 — 装饰性宣称仍拦]
  PASS: TC2 裸 X/Y PASS 无命令 → fail
  PASS: TC3 命令距离 >10 行 → fail (不算证据)
  PASS: TC3b 表格排版 (命令隔 6 行) → 豁免

[正向 — raw output 放行]
  PASS: TC4 X/Y PASS + $ bash 命令 → 豁免
  PASS: TC5 X/Y PASS + exit=0 → 豁免
  PASS: TC6 X/Y passed + rc=0 → 豁免

[其他 blacklist 词无例外]
  PASS: TC7 其他词 (协同/收尾类) 有命令也不豁免
```

TC2 / TC3 是关键 — 证明例外**没有变成后门**:
- 裸数字 (如 `25/25` 后跟 PASS) 附近无命令 → 仍 fail

TC3b 是窗口调整的依据: ±5 行太窄, "命令 + 空行 + 表头 + 分隔行 + 3 行数据" 就超了.
调到 ±10 后表格排版能过, 隔一整段的无关命令仍不算.

TC1 防 pattern 漂移 (脚本里的 regex 必须跟 blacklist 里的字面相同).
