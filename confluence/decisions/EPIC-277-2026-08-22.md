## 0. 一句话总览

EPIC-277 Sprint 暴露的不是 6 个独立 bug, 而是**主公开发流程的 5 个系统性缺口**: (1) 派工 prompt 缺必跑项, (2) 并行改 immutable 缺 cross-check, (3) 派单数字缺实测, (4) hook 环境差异缺实测, (5) 算法 + 阈值缺基础设施型考虑。每个缺口都跨项目可复用。

## 1. 错题 #1: 派工 prompt 缺必跑项 (ranked #1, 治根 已落)

### 症状
subagent 报 "5-Level Verify 全绿", 推 PR 后 CI FAIL — 8 ESLint errors。**subagent self-report ≠ 实跑 raw output**。

### 根因 (跨项目普适)
- subagent 跑 `npm run build` + `vitest run` 报告 PASS,但**跳 lint** (CLAUDE.md §2 L2 硬要求 `cargo test --workspace --release`, subagent 读不出 lint 项)
- subagent 输出 ≠ 独立验证: **subagent 既是 report author 又是 verifier**, 共享同一推理路径 (跟 EPIC-270 复盘 53 PR reviews=0 同型)
- card 派单 prompt 自由发挥, 缺乏 5 必跑项硬编码

### 治根 (跨项目可复用模板)
**5-Level Verify 必跑 5 项** (派工 prompt 硬编码):
1. `npm run lint` (或对应 linter)
2. `npm run build` (或 `cargo build` / `go build` / etc.)
3. test runner (vitest / cargo test / go test / pytest)
4. `bash scripts/scan-dead-code.sh` (或死代码检测)
5. `bash scripts/hooks/install.sh --verify` (或安装验证)

**Rule 34 + EPIC-270 联合应用**:
- subagent 报 PASS ≠ master 不验证. master 必查 subagent 实跑 raw output (跟 Rule 34 "Performer 独立复现" 1:1)
- PR body 必含 raw test output (file path + line), 跟 `check-claim-evidence.sh` gate 联合
- T1/T2/T3 review tier (跟 EPIC-270) 跟必跑项挂钩, T3 必独立 subagent 核实

### 验证指标
- 派工后 subagent 报 PASS → master 必 `git log -p` + 实跑 5 必跑 (不只看 subagent self-report)
- PR 描述 raw test output 长度 ≥ 5 行 / 测试 (跟 `check-claim-evidence.sh` exit 1 = 拒)
- subagent 跳必跑项 = 报 ticket status `blocked` + 重新派工

## 2. 错题 #2: 并行改 immutable 缺 cross-check (ranked #2, 治根 已落)

### 症状
两个 subagent 并行跑 (D + E), 都改 `CLAUDE.md` + `.claude/rules/immutable-scripts.md` + `install.sh` + `pre-commit` 4 文件 → rebase 时 4 文件全 conflict, master 手工 resolve 30 分钟。

### 根因 (跨项目普适)
- Rule 35 "≥4 模块 / ≥5 文件 → 必须拆 EPIC" 是**单卡**约束, **不约束多卡并行**
- sprint-metrics 派工前 master 没做 cross-check: 卡 X 改 immutable 时, 同步看其他 in-flight 卡是否也改 immutable
- subagent 派工 prompt 不暴露"哪些文件是 immutable" (只暴露 ticket scope)

### 治根 (跨项目可复用)
**Sprint 派工前 master 必做 cross-check** (跟 retrospective-routine 阶段 1 联合):
1. 列出 in-flight 卡 (sprint-metrics `--epic` 看 worktree)
2. 列出各卡 file_scope.includes
3. 交集 ≥ 2 immutable 文件 → 标 **parallel-conflict-risk** 标识
4. 冲突标识: 二选一 (a) 串行 (后者等前者 testing merge) (b) 拆卡原则细化 "单 Sprint ≤2 卡碰 immutable"

**拆卡原则细化** (跟 Rule 35 §2 联合):
- 单卡 ≤4 文件 + ≤100 行 commit (跟 Rule 8 Rule-of-500 联合)
- 单 Sprint ≤2 卡碰 immutable (新增)
- 并行卡 file_scope diff > 50% 才并行, 否则串行

### 验证指标
- sprint-metrics `mis_dispatch_rate` 跟"scope_conflict" 强相关. scope_conflict ↑ = 跨 specialization 派单 = 错派率 (跟 #5 联合)
- rebase conflict 0 (FF push 干净) 是单 Sprint 闭环最低标准
- 卡 D/E 并行触发 `mis_dispatch_rate` 75% FAIL 量化证据, 是该错题的可观察代理

## 3. 错题 #3: 派单数字缺实测 (ranked #3, 治根 已落)

### 症状
派单 AC 写 "270+ 历史 ticket review 回填", subagent 实测仓里只 **212 个 EPIC ticket.json**. AC 写 "EPIC-230 4/4 PASS", 实测仓里没 EPIC-230, 且 `expert_activation_rate ≥5` 需 daemon 长期生产积累 (一次 commit 造不出, 硬造=伪造数据源).

### 根因 (跨项目普适)
- ticket.json AC 数字是**主公拍板时估算**, 没跑实测 (`find | wc -l`)
- subagent 接手时**没独立验证 AC 数字** (跟 Rule 34 Performer 独立复现缺失同型)
- AC 数字 vs 实测的 gap 没在 PR body 显式披露 (跟 BE-26 "诚实修正" 战略缺失)

### 治根 (跨项目可复用)
**建卡前 master 必跑实测 + AC 数字带实测 footer**:
- 建卡前 5 必实测 (跟错题 #1 同):
  1. `find jira/tickets -name ticket.json | wc -l` (ticket 数)
  2. `git log --oneline | wc -l` (commit 数)
  3. `git diff --stat origin/main..HEAD` (改动 stat)
  4. ticket.json 字段实测 (grep `.performer` etc.)
  5. AC 涉及的 metric 实测 (跟 sprint-metrics 联合)
- AC 数字带 footer: `实际 X/Y 跟 commit 时实测为准`
- subagent 接手后必独立复现 AC 数字 (跟 Rule 34 1:1)
- 数字不符必**诚实修正 + PR body 透明披露** (BE-26 战略)

### 验证指标
- PR body "自动验证" 段必含 raw `find | wc -l` / `git log | wc -l` 输出
- AC 数字跟实测 gap > 10% = subagent 必报 ticket status `blocked` + 上报 master
- 跨 Sprint 累计: 数字不符 ticket 数 0

## 4. 错题 #4: hook 环境差异缺实测 (ranked #4, 治根 已落)

### 症状
6 个 hook 脚本 `git -C <script_dir> rev-parse --show-toplevel` 在 git hook 环境 (`GIT_DIR` 已设) 下返回 `-C 目录` 而非 repo root → BLACKLIST/BASELINE 路径拼成 `scripts/hooks/jira/tickets/...` → fail-closed 拦死每次 commit.

### 根因 (跨项目普适)
- subagent 跑 hook dry-run 不触发 `GIT_DIR` (git config 上下文与 hook 上下文不同)
- subagent 没在**真 hook 环境**实测 (跟错题 #1 同样的 self-report 缺失, 但触发条件更隐蔽)
- 6 个新脚本统一写 `git -C <script_dir> rev-parse --show-toplevel` 都踩同一陷阱, 缺统一 helper
- 跟 EPIC-224 "core.hooksPath 指向已删临时目录" 同型, **hook 激活 ≠ hook 实际生效** ("脚本存在 ≠ 脚本生效")

### 治根 (跨项目可复用)
**Hook 写必跑 4 步实测** (跟错题 #1 派工模板联合):
1. `git config core.hooksPath` 设到 .git/hooks 真路径
2. 实跑 commit 触发 hook (不 dry-run)
3. 验证 hook exit code 跟设计一致 (0=PASS, 1=FAIL, 3=SKIP)
4. 验证 hook 改的 path 跟设计一致 (用 `env -u GIT_DIR -u GIT_WORK_TREE` 兜底)

**统一 helper 模板** (跨脚本共享):
```bash
# canonical repo root, env-agnostic
REPO_ROOT="$(env -u GIT_DIR -u GIT_WORK_TREE git -C "$(cd "$(dirname "${BASH_SOURCE[0]}")" && pwd)" rev-parse --show-toplevel 2>/dev/null || \
  env -u GIT_DIR -u GIT_WORK_TREE git rev-parse --show-toplevel 2>/dev/null || pwd)"
```

**防复发 test** (每项目必建):
- `tests/integration/hook-environment-scan.test.sh`: 模拟 GIT_DIR 已设, 扫所有 hook 脚本, 验不踩陷阱
- 跟 EPIC-224 install.sh `--verify` 联合, CI 必跑

### 验证指标
- `install.sh --verify` 9/9 PASS (跟 EPIC-277-E 1:1)
- hook-environment-scan.test.sh 8/8 PASS (跟 EPIC-277-G 1:1)
- 实跑 `git commit` 在 hook 环境 exit code 0 + 实际改 path 跟设计 1:1

## 5. 错题 #5: 算法 + 阈值缺基础设施型考虑 (ranked #5, 治根 已落)

### 症状
sprint-metrics `mis_dispatch_rate` 75% FAIL (3/4 scope_conflict) — 卡 D/E/F/G 4 ticket 真跨 backend+test+docs 3 specialization, 但算法把"跨多 spec" = "scope_conflict" = 错派, 对**基础设施型 EPIC** 不公平.

### 根因 (跨项目普适)
- 任何 metric 算法都基于**简化假设** (跟 BE-25 独立 subagent 不够独立同型)
- 阈值 (60% / 10%) 跟"基础设施型 EPIC 跨多 spec 是设计" 不匹配
- ticket.json 无"故意跨多 spec" 标记字段, 算法无法区分"有意" vs "无意"

### 治根 (跨项目可复用)
**3 步组合** (跟错题 #1 派工模板 + 错题 #3 数字实测联合):
1. **allow-list per ticket**: ticket.json 加 `multi_spec_intentional: true` 字段, 跳过 scope_conflict 检查
2. **阈值放宽**: 基础设施型 EPIC 跟 docs-only EPIC 拆阈值 (cross_epic_reuse 60%→40%)
3. **新指标** (跨 Sprint): `cross_spec_intentional_rate` ≥50% PASS, 取代 `mis_dispatch_rate`

**算法升级 + ticket.json 字段 + 阈值 3 处同步** (跟 EPIC-223 改数字强制流程 §3 1:1):
- 任何指标变化 (60% → 40%) 必须**同时**改 3 处 (CLAUDE.md / SKILL.md / metric-thresholds.md)

### 验证指标
- sprint-metrics `mis_dispatch_rate` ≥ 90% EPIC PASS (治根目标)
- ticket.json 字段覆盖率 100% (基础设型 EPIC 全标)
- 算法 + ticket.json 字段 + 阈值 3 处同步率 100% (改数字强制流程)
- `multi_spec_intentional_skip` breakdown 字段 出现 (新指标透明度)

## 6. 错题 #6: ticket.json 改字段缺 jq 验证 (ranked #6, 治根 已落)

### 症状
2 次坏 JSON 实战:
- EPIC-150-D ticket.json 行 29 多余 `}` 提前闭合 (历史遗留)
- EPIC-277-G ticket.json `reproduction_command:":` 双冒号 (我建卡时手误)

两者都让 `jq . ticket.json` parse fail, 导致 sprint-metrics 跑 mis_dispatch 时**字段读不出**, 算法失真.

### 根因 (跨项目普适)
- 改 ticket.json 后**没立即验证**: 直接 commit + push, 等 CI 才暴露 (跟错题 #1 同样的延迟反馈)
- ticket.json 写错**没成本可见**: 单字符 typo (`:":`) 不影响 schema, 但 jq 直接 fail
- 跟错题 #1 同型: subagent / master 写完没立即 `jq .` 验证, 跳实测

### 治根 (跨项目可复用)
**改 ticket.json 后必跑 3 步验证** (跟错题 #1 #3 #4 联合):
1. `jq . <file>` exit 0 + 合法结构
2. `jq -r '.<field>' <file>` 验证字段类型 (boolean 字段验 `true`/`false` 字面)
3. `bash scripts/hooks/check-ticket-schema.sh <file>` 跟 EPIC-223 联合, 验 required_fields

**commit-msg gate** 升级: 改 ticket.json 的 commit, hook 必验 `jq .` 通过.

**双冒号 / 多余符号防御**:
- bash heredoc 写 JSON 不用, 用 `jq -n` build object (强类型)
- ticket.json 模板从 `jira/tickets/.archive-baseline.json` 跟 EPIC-280 风格统一

### 验证指标
- 改 ticket.json → push → CI ticket-schema check exit 0
- 双冒号 / 多余符号出现 0 (跟 EPIC-252 jargon 1:1 跨错别字 gate)
- sprint-metrics emit 全 7 指标 (退 0 fields 0 字段)
