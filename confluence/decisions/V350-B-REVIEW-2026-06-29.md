### [S-001] P0 — graceful-exit.sh "实战 1 次" 是 fake theatre (pgrep 0 命中, 0 进程被关闭)

**证据**:
- `scripts/graceful-exit.sh:17-38` — 6 步 全部 `pgrep -f "hook.*server" / web.*dashboard / node.*src / kallax.*binary`, **只 call `pkill` 不 verify 实际关掉**
- `scripts/graceful-exit.sh:8` echo "🚪 KALLAX graceful-exit" **没解析任何 args** — 无 `--dry-run` / `--actual` flag

  ```
  🚪 KALLAX graceful-exit (跟 eket Level 4 1:1 联合, 跟反讽 联合)
    → 关闭 Shell 层 (兜底, 跟 eket Level 4 1:1)
  ✅ KALLAX graceful-exit 落地 (跟 eket Level 4 1:1 联合, 跟 v3.4.0 累计 联合)
  ```
  0 个 audit / hook / web / node / rust 被关闭 — pgrep 0 命中 → 全部 `if` 跳过 → 只 echo "Shell 层 兜底"
- v3.5.0 evidence `docs/evidence/v3.5.0/graceful-exit-actual.txt` (216B) **= `graceful-exit-dryrun.txt` (216B)** — diff 是 0 行! 跟 V350-RELEASE §2 "实战 1 次" claim **完全矛盾**
- v3.4.0 evidence `docs/evidence/v3.4.0/graceful-exit-actual.txt` (342B) 含 6 步全部 echo — 但脚本本身没分支逻辑, "actual" vs "dryrun" 区别是手工 copy paste

**攻击场景**:
1. 主公/用户跑 `bash scripts/graceful-exit.sh --actual` 以为真关闭 → 实际 0 进程被关闭 (pgrep 0 命中)
2. KALLAX 5 个进程 (audit chain / hook server / web dashboard / node / rust) 仍跑 → 用户重启时 端口冲突 / data corruption
3. v3.5.0 evidence 跟 dryrun 1:1 byte-identical → "实战 1 次" 是 0 真实 — 跟 v3.1.0 P-002 "0 装饰引用 self-contradict" 同模式 反讽

- P0-a: `graceful-exit.sh` 加 `--dry-run` / `--actual` flag (用 `getopts`), `--actual` 必须先启 6 类 mock 进程再 kill + verify

### [S-002] P0 — graceful-exit.sh 自身无 signal handler (SIGTERM / SIGINT 跟 eket 1:1 缺)

**证据**:
- `scripts/graceful-exit.sh:1-44` — 仅 plain script, **0 trap / 0 signal handler**, `set -euo pipefail` (line 6) 但 `kill -TERM $$` 仍 terminate
- `node/src/utils/process-cleanup.ts:99-110` Node.js 端有 `SIGINT / SIGTERM / SIGHUP` handler + cleanup handlers — 但 graceful-exit.sh 是 **独立 shell script**, 不 share Node.js 进程组
- V350-RELEASE-2026-06-30.md §2 写 "6 步 落地: audit chain 关闭 → hook server 关闭 → ... → Shell 层兜底" — 但 graceful-exit 本身是被人工跑, 没人调 signal
- `scripts/graceful-exit.sh:17-38` 用 `pkill -f "hook.*server"` — pattern `hook.*server` **match 太多** (e.g. claude-code 的 hook server 自己, dev tools like pm2), 可能误杀 同机其它进程

**攻击场景**:
1. User 按 Ctrl+C 跑 `bash graceful-exit.sh` → 6 个 `pkill -f` 还没跑完就 terminate → audit chain 半关 → data corruption (audit log 半写)
2. `pkill -f "node.*src"` 在 Node.js 项目目录跑 → 误杀同机其它 dev node process (e.g. `vite`, `webpack-dev-server`) — `node.*src` pattern 太泛
3. `pkill -f "kallax.*binary"` 跟 `pgrep -f "kallax.*binary"` 都用 broad pattern — Linux macOS `pgrep` 也可能 match 当前 `grep -f` 自己的 cmdline (race condition: pgrep → pkill 之间 P 死了)
4. 跟 Node.js `process-cleanup.ts` 不联动 — KALLAX main process exit 时 graceful-exit.sh 不被自动调 → 实际 0 integration

**修复建议** (跟 Rule 17 文件并发 5 步 联合, 跟 eket Level 4 graceful-exit 1:1 联合):
- P0-a: 顶部加 `trap 'log "interrupted"; exit 130' SIGINT SIGTERM` + `set -e` 失败清理
- P0-b: 替换 broad pattern — `pkill -f` → `pkill -f "kallax-hook-server\.js"` (精确 binary 名) + `pgrep` 后 verify PID 在 `.kallax/pid/` 已知 PID file 才 kill
- P0-c: 写 `pid_dir` (`.kallax/pid/`) 集中 PID 跟踪, graceful-exit 读 PID file 而不是 pgrep
- P1: Node.js `process-cleanup.ts` exit 时 exec `scripts/graceful-exit.sh` (signal bridge, 跟 eket 4 级降级 L4 1:1)

### [S-003] P0 — ioredis `password` 字段 via `RedisPubSubConfig` 无凭据脱敏 (log 泄露)

**证据**:
- `node/src/core/redis-pubsub.ts:68-82` — `new Redis({ host, port, password, db, ... })` 把 password 直接 in-memory
- `node/src/core/redis-pubsub.ts:131-142` — `publisher.on('error', (error) => logger.error({ error: error.message, host, port }, '...'))` — **error 消息 ioredis 经常含 `password=***` 部分 or AUTH fail stack trace**, 直接 emit 到 log
- `node/src/core/master-election.ts:40` — `logger.warn({ error: error.message, redisUrl }, 'redis connect failed')` — `redisUrl` 全 URL `redis://:password@host:port` 可能 in log
- `node/src/core/redis-pubsub.ts:34` `password?: string` — 但 `RedisPubSubConfig` 的 caller (e.g. `MessageQueueConfig.redis`) **没 enforce secret loading via secret manager**
- `docs/guides/deployment-2026-06-19.md:47 / 126` 示范 `REDIS_URL=redis://localhost:6379` (无 auth) — deployment doc 没说 "production must use auth" — user 部署时无 password → KALLAX 默认 fail-open 到 no-auth Redis

**攻击场景**:
1. KALLAX Redis password 写 deployment YAML / env var → env dump 进 log (e.g. `kubectl describe pod`) → attacker 读 log 拿 Redis full access
2. ioredis v5.4.0 `error.message` 含 stack frame including config object (历史 CVE 类似 GHSA-xxx) → log → leak
3. Redis server 无 auth 部署 → KALLAX 静默接受 no-auth connection → 攻击者 write `kallax:master:lock` 抢 master election (跟 S-005 联合)
4. 跟 v3.1.0 S-001 `kallax-dev-key` 硬编码 default 是同模式 (凭据 fail-open) — v3.1.0 治 S-001 但 v3.5.0 新增 ioredis 路径 仍 fail-open

**修复建议** (跟 V310-B S-001 治根 模式 1:1 联合):
- P0-a: `redis-pubsub.ts:131-142` 加 redaction — `logger.error({ error: redactPassword(error.message), host, port }, ...)` (跟 `audit-middleware.ts` 已有 redaction 模式 1:1)
- P0-b: `master-election.ts:40` 改 `redactUrl(redisUrl)` (mask `:password@` → `:***@`)
- P0-c: `.kallax/config.yml` 加 `redis.required_auth: true` (跟 v3.1.0 S-001 fail-closed 联合), 无 password → fail-fast 启动
- P1: pre-commit hook `check-redis-auth.sh` (grep `Redis(.*password` 全 codebase, verify logger call 全 redact)
- P1: `docs/guides/deployment-2026-06-19.md` 加 "production 必设 `requirepass`, KALLAX 启动时 verify PING AUTH 成功"

### [S-005] P1 — `master-election.ts` redisPool 单例不 close 旧连接 (连接泄漏)

**证据**:
- `node/src/core/master-election.ts:21-43`:
  ```ts
  const redisPool = new Map<string, Redis>();
  async function getRedis(redisUrl: string): Promise<Redis | null> {
    let redis = redisPool.get(redisUrl);
    if (redis && redis.status === 'ready') return redis;
    // Create or recreate
    redis = new IORedis(redisUrl, { ... });
    await redis.connect();
    redisPool.set(redisUrl, redis);
    return redis;
  }
  ```
  — `if (redis.status === 'ready')` 之外路径 (e.g. `connecting` / `reconnecting` / `end`) **直接 overwrite** `redisPool.set(redisUrl, redis)`, **旧连接无 `.quit()` 调用**
- 旧连接 ioredis 实例仍持有 socket fd → Redis server 端 `CLIENT LIST` 显多连接 → fd leak
- `master-election.ts` 没 import `process-cleanup.ts` → Node.js exit 时 Redis 连接不 close (跟 S-002 联合)
- v3.5.0 release 主张 "实战 eket ioredis 1 次" 但 connect-leak 治理剧场 — 1 次实测可能 fd leak

**攻击场景**:
1. KALLAX 跑 24h, master-election 重试 100 次 → Redis server 端 `CLIENT LIST` 100 stale connection → fd 上限 → Redis 拒绝新连接 → master-election 全 fail → 集群无 master
2. KALLAX 重启 → 旧 redisPool map 在 Node.js heap 仍引用 (Node GC 不一定 close) → 慢 leak
3. 跟 S-004 `probeRedis` 恒 true 联合 → leak 看不出 → 直到 Redis server OOM 才爆

**修复建议** (跟 `redis-pubsub.ts:144-161` 已有 `registerCleanupHandler` 模式 1:1 联合):
- P1-a: `master-election.ts:43` 加 `registerCleanupHandler('redis-election-pool', async () => { for (const r of redisPool.values()) await r.quit(); redisPool.clear(); })`
- P1-b: `getRedis` overwrite 旧 connection 前先 `old?.quit()` (try/catch)
- P1-c: 加 `tests/integration/election-leak-test.sh` (跑 100 次 getRedis, 验证 Redis server `CLIENT LIST | wc -l` < 5)
