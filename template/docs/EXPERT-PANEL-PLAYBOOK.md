### 1.2 核心专家 (5 人)

| 角色 | 专长 | 触发条件 |
|-----|------|---------|
| 系统架构师 | 系统设计、技术选型 | 新功能设计、大规模重构 |
| 安全专家 | 安全审计、威胁建模 | 认证授权变更、敏感数据处理 |
| 性能专家 | 性能优化、容量规划 | 关键路径变更、高并发场景 |
| 测试专家 | 测试策略、质量保证 | 复杂边界条件、测试覆盖争议 |
| 领域专家 | 业务规则、领域建模 | 业务逻辑变更、新领域引入 |

## 2. 触发条件

### 2.1 自动触发

```yaml
expert_panel_triggers:
  # 系统架构师
  system_architect:
    - new_service_design
    - database_schema_change
    - api_breaking_change
    - technology_selection
    - cross_service_integration
    
  # 安全专家
  security_expert:
    - auth_change
    - encryption_change
    - pii_handling
    - third_party_integration
    - access_control_change
    
  # 性能专家
  performance_expert:
    - critical_path_change
    - database_query_optimization
    - caching_strategy
    - concurrency_handling
    - resource_intensive_operation
    
  # 测试专家
  test_expert:
    - test_strategy_change
    - complex_boundary_conditions
    - flaky_test_investigation
    - coverage_dispute
    
  # 领域专家
  domain_expert:
    - business_rule_change
    - new_domain_introduction
    - workflow_modification
    - data_model_change
```

### 2.2 手动触发

```bash
# Conductor 主动召集专家组
kallax expert:convene --topic "用户认证重构方案" --experts architect,security

# Performer 请求专家意见
kallax expert:consult --expert performance --question "Redis 缓存策略选择"
```

## 3. 工作流程

### 3.1 标准流程 (5 阶段)

```
┌─────────────────────────────────────────────────────────────────────┐
│                     专家组工作流程                                   │
├─────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  Phase 1: 召集 (Convene)                                            │
│  ───────────────────────                                            │
│  • Conductor 确定议题                                               │
│  • 选择相关专家                                                     │
│  • 准备背景材料                                                     │
│  • 设定截止时间                                                     │
│                          │                                          │
│                          ▼                                          │
│  Phase 2: 独立评审 (Independent Review)                             │
│  ─────────────────────────────────────                              │
│  • 各专家独立分析                                                   │
│  • 形成初步意见                                                     │
│  • 标记关注点                                                       │
│  • 提出问题                                                         │
│                          │                                          │
│                          ▼                                          │
│  Phase 3: 汇总讨论 (Synthesis)                                      │
│  ─────────────────────────────                                      │
│  • 收集所有意见                                                     │
│  • 识别共识点                                                       │
│  • 标记分歧点                                                       │
│  • 整理待讨论问题                                                   │
│                          │                                          │
│                          ▼                                          │
│  Phase 4: 决策 (Decision)                                           │
│  ────────────────────────                                           │
│  • 分歧点讨论                                                       │
│  • 投票 (如需要)                                                    │
│  • 形成最终决策                                                     │
│  • 记录决策理由                                                     │
│                          │                                          │
│                          ▼                                          │
│  Phase 5: 记录 (Documentation)                                      │
│  ─────────────────────────────                                      │
│  • 创建 ADR (如适用)                                                │
│  • 更新知识库                                                       │
│  • 通知相关方                                                       │
│  • 归档讨论记录                                                     │
│                                                                      │
└─────────────────────────────────────────────────────────────────────┘
```

### 3.2 快速通道

对于紧急决策，使用简化流程:

```
紧急决策流程:
1. Conductor 发起紧急召集
2. 单个最相关专家给出意见
3. Conductor 做出决策
4. 事后补充完整评审
```

## 4. 专家职责

### 4.1 系统架构师

**职责范围**:
- 系统整体架构设计
- 技术选型决策
- 模块划分与依赖
- API 设计原则
- 可扩展性评估

**评审要点**:
```markdown
## 架构评审清单

### 设计原则
- [ ] 单一职责: 每个模块职责明确
- [ ] 开闭原则: 对扩展开放，对修改关闭
- [ ] 依赖倒置: 依赖抽象而非具体
- [ ] 接口隔离: 接口小而专一

### 系统设计
- [ ] 分层清晰: 表现层/业务层/数据层
- [ ] 依赖方向正确: 上层依赖下层
- [ ] 无循环依赖
- [ ] 关注点分离

### 可维护性
- [ ] 模块可独立部署
- [ ] 配置外部化
- [ ] 日志可追踪
- [ ] 监控可观测
```

### 4.2 安全专家

**职责范围**:
- 安全威胁建模
- 认证授权方案
- 数据保护策略
- 漏洞评估
- 合规性检查

**评审要点**:
```markdown
## 安全评审清单

### 认证授权
- [ ] 认证机制安全 (JWT/OAuth)
- [ ] 授权粒度合适 (RBAC/ABAC)
- [ ] Session 管理正确
- [ ] Token 过期策略合理

### 数据保护
- [ ] 敏感数据加密存储
- [ ] 传输层加密 (TLS)
- [ ] PII 处理合规
- [ ] 日志脱敏

### 输入验证
- [ ] 所有输入验证
- [ ] SQL 注入防护
- [ ] XSS 防护
- [ ] CSRF 防护

### 访问控制
- [ ] 最小权限原则
- [ ] 资源访问检查
- [ ] 操作审计日志
```

### 4.3 性能专家

**职责范围**:
- 性能瓶颈识别
- 优化策略建议
- 容量规划
- 缓存策略
- 并发处理

**评审要点**:
```markdown
## 性能评审清单

### 数据库
- [ ] 查询优化 (无 N+1)
- [ ] 索引设计合理
- [ ] 连接池配置
- [ ] 事务范围最小化

### 缓存
- [ ] 缓存策略合适
- [ ] 缓存失效处理
- [ ] 缓存穿透防护
- [ ] 缓存有 TTL

### 并发
- [ ] 并发安全
- [ ] 锁粒度合理
- [ ] 无死锁风险
- [ ] 资源池化

### 容量
- [ ] 负载评估
- [ ] 扩展方案
- [ ] 降级策略
```

### 4.4 测试专家

**职责范围**:
- 测试策略制定
- 测试覆盖评估
- 边界条件识别
- 测试质量保证
- 自动化测试指导

**评审要点**:
```markdown
## 测试评审清单

### 测试策略
- [ ] 测试金字塔合理
- [ ] 单元测试覆盖核心逻辑
- [ ] 集成测试覆盖交互
- [ ] E2E 测试覆盖关键路径

### 测试质量
- [ ] 测试独立可重复
- [ ] 无内联实现复制
- [ ] 边界条件覆盖
- [ ] 错误路径覆盖

### 覆盖率
- [ ] 行覆盖 >= 80%
- [ ] 分支覆盖 >= 75%
- [ ] 关键路径 100%
```

### 4.5 领域专家

**职责范围**:
- 业务规则理解
- 领域模型设计
- 业务流程验证
- 术语定义
- 边界界定

**评审要点**:
```markdown
## 领域评审清单

### 业务理解
- [ ] 业务需求准确理解
- [ ] 业务规则完整捕获
- [ ] 边界条件明确

### 领域模型
- [ ] 实体定义准确
- [ ] 值对象识别正确
- [ ] 聚合边界清晰
- [ ] 领域事件完整

### 术语统一
- [ ] 术语与 Glossary 一致
- [ ] 无二义性表达
- [ ] 代码命名符合领域语言
```

## 6. 决策机制

### 6.1 共识决策

优先追求共识:

```
1. 识别共同点
2. 缩小分歧范围
3. 寻找折中方案
4. 形成一致意见
```

### 6.2 投票决策

当无法达成共识时:

```yaml
voting_rules:
  # 投票权重
  weights:
    system_architect: 1
    security_expert: 1
    performance_expert: 1
    test_expert: 1
    domain_expert: 1
    conductor: 1  # Conductor 有投票权
    
  # 通过条件
  pass_threshold: 0.6  # 60% 支持
  
  # 特殊情况
  security_veto: true   # 安全专家对安全问题有否决权
  architect_veto: true  # 架构师对架构问题有否决权
```

### 6.3 升级决策

当专家组无法决策时:

```bash
# 升级到人类决策
kallax decision:escalate --topic "议题" --reason "无法达成共识"

# 记录到 human_feedback
# Human 做出决策后继续
```

## 7. 知识沉淀

### 7.1 ADR 创建

重要决策必须创建 ADR:

```bash
# 创建 ADR
kallax adr:create "选择 PostgreSQL 作为主数据库"

# ADR 模板
confluence/decisions/ADR-NNN.md
```

### 7.2 知识库更新

```bash
# 更新相关知识
kallax knowledge:update --topic patterns --file caching-strategy.md

# 更新术语表
kallax glossary:add "CAP 定理" "分布式系统中一致性、可用性、分区容错性三者最多只能同时满足两个"
```

### 7.3 案例归档

```yaml

location: confluence/memory/expert-cases/

  # 案例: [议题]

  ## 决策
  [最终决策]
  
  ## 经验教训
  [可复用的经验]
```

## 8. 配置

```yaml
# .kallax/config.yml
expert_panel:
  # 核心专家
  core_experts:
    - system_architect
    - security_expert
    - performance_expert
    - test_expert
    - domain_expert
    
  # 超时设置
  timeouts:
    independent_review: 24h    # 独立评审时间
    synthesis: 4h              # 汇总时间
    decision: 8h               # 决策时间
    urgent_total: 4h           # 紧急决策总时间
    
  # 触发配置
  auto_trigger: true
  trigger_rules_file: ".kallax/expert-triggers.yaml"
  
  # 输出配置
  output:
    adr_required_for_decisions: true
    archive_all_discussions: true
```
